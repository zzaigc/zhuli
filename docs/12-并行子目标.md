# 12-并行子目标（v0.3.0）

> 本文档讲的是 v0.3.0 新增的「并行子目标」：把一次规划得到的子任务
> 分组，组按顺序执行，组内独立子任务的思考并行、工具执行串行。
> 它是 Nova 式并行规则的 Zhuli 改写（规则重写实现，不是复制代码），
> 适配 Zhuli 的异步编排器，而不是照搬 Nova 的实现。

## 一句话

独立的事情可以一起想，但动手（工具调用）永远排队一个一个来；
浏览器步骤和 Hive 模式永远不并行。

## 为什么只并行「思考」，不并行「动手」

- Zhuli 的实时主循环是单页面、步步依赖的：每一步的观察都依赖
  上一步的结果，多个浏览器步骤还共用同一个页面。把页面步骤并行，
  页面状态会互相打架，结果不可复现。
- 所以并行只发生在子任务单元级别：每个子任务的「思考」（LLM 推理、
  准备动作）可以并发；一旦要真正动手（工具调用、改共享状态），
  就必须排队，同一瞬间只允许一个工具调用在跑。
- 速度收益来自思考并行，正确性靠工具锁保证。误判只损失速度，
  不损失正确性（见「误判代价」）。

## 分组规则（`src/zhuli/core/parallel.py` 的 `plan_groups`）

规划器只把「独立」子任务分进同一组，出现以下任一情况就另起一组：

1. **浏览器步骤永远单组**：工具是 `browser`，或文本含浏览器关键词
   （浏览器、网页、页面、点击、打开网页、跳转、截屏、表单等）。
2. **依赖步骤不与被依赖者同组**：文本含「然后、接着、基于上一步、
   用上一步的结果、previous」等依赖词时，另起一组（它必须在被
   依赖者之后执行）。
3. **共享可变资源的步骤不与同组**：同一文件路径（如 `report.md`）、
   同一工具目标（codebuddy/trae/opencode/shell/video 等）、同一引用
   字符串出现在组内已有成员时，另起一组。
4. 其余步骤可同组。

规划失败、输入非法时，分组回退为「全部单步、顺序执行」，绝不抛错、
绝不按坏分组执行。

## 第二道防线（`sanitize_groups`，执行前再校验）

即使上游规划已经给出了分组，执行器在真正执行前还会重新检查一次：

- 任何含浏览器步骤或浏览器关键词的组，一律拆回单步；
- 组内出现共享资源时，按分组规则重新分组；
- 空组、空字符串等非法分组会被清洗掉。

这道防线存在的意义是：规划器分错组也不致命，执行器会把它纠正。
误判（本来可以并行却被拆开）只损失一点速度，不会错。

## 执行规则（`ParallelRunner` / `run_parallel_groups`）

- **组按顺序执行**：第 1 组全部完成，才开始第 2 组。
- **组内思考并发**：用 `asyncio.gather` 同时跑各子任务的 `think`，
  结果按组内顺序保存（`gather` 的返回顺序就是传入顺序）。
- **组内工具串行**：各子任务的 `execute` 在同一把 `asyncio.Lock`
  下按组内顺序执行，工具调用永远不会在同一瞬间发生；共享状态的
  更新也在锁下进行。
- **失败兜底**：并行组执行失败时，整组顺序重跑（思考+执行各一步）；
  顺序重跑也失败时，异常向上传递，由调用方决定重规划或停机，
  绝不静默丢弃。并行思考失败时，残留的思考任务会被先取消，
  再开始顺序重跑，避免残留任务污染重跑（这是测试中真实捕获并
  修掉的问题）。
- **结果合并**：每组返回一个 `GroupResult`（组序号、组内子任务、
  按顺序的结果、是否回退过顺序重跑、是否本来就是顺序执行）。

## 开关（默认开，关了一定生效）

三处，优先级：运行时覆盖 > Hive 强制关闭 > 配置。

| 方式 | 写法 | 作用范围 |
|---|---|---|
| 配置 | `policy.parallel_enabled: true/false`（`config/settings.yaml`，示例文件已加） | 默认值，默认开 |
| 控制台 | Hive 面板内的「并行子目标」开关，调用 `GET/POST /api/parallel` | 运行时覆盖，只在内存中，重启恢复配置值 |
| 命令行 | `zhuli --no-parallel` | 启动时把运行时覆盖设为关，同样不改写配置文件 |

关闭时，所有分组退化为单步，执行与 v0.2.0 完全一致。
控制台 `/api/parallel` 还会返回当前计划的分组（`groups` 字段），
供检查「这次计划到底怎么分的」。

## 与 Hive 的关系（不双重并行）

- Hive 模式本身已经是「多个执行体并行提案 + 加权投票择优」，
  投票是按「一次决策」算的。
- 如果子任务分组再叠加一层并行，两个并行机制会互相干扰：投票
  针对的决策不再唯一，胜出者的执行顺序也无法保证。
- 所以 **Hive 开启时，并行子目标强制关闭**：`effective_parallel`
  在 Hive 下恒为 False，`plan_groups` 返回全部单步，控制台开关
  也会显示「Hive 模式强制顺序」。关掉 Hive 后，并行按配置/覆盖恢复。
- Hive 的 token 消耗约为普通流水线的 3 倍（v0.2.0 已说明），并行
  子目标本身不额外乘以 Hive 的倍数，因为它在 Hive 下根本不生效。

## 主循环的关系（诚实边界，必须说清楚）

- v0.3.0 的并行分组已接入主循环的计划阶段：每次生成初始计划后，
  编排器会计算分组、存到 `orchestrator._parallel_groups`，并以一条
  计划阶段的思考事件把分组推到控制台（控制台 `/api/parallel` 的
  `groups` 就是它），用户能看见「这次计划怎么分的」。
- 但**实时浏览器主循环本身仍顺序执行**：它的每一步观察依赖上一步
  结果、且多步共用同一页面，并行分组不直接改写主循环。并行执行
  由 `orchestrator.run_parallel_groups(groups, think, execute)` 承担，
  用于独立的非浏览器子任务单元（思考并行、工具串行），主循环将来
  重构为「子任务单元」驱动后可以直接接管该分组。
- 因此 v0.3.0 不声称「浏览器任务变快了」：浏览器任务的速度与
  v0.2.0 相同，并行收益只发生在独立子任务单元的思考阶段。

## 测试（`tests/test_parallel.py`，标准库 unittest，无第三方依赖）

Zhuli 原项目没有测试目录，本版新增 `tests/test_parallel.py`，
用假智能体/桩步骤验证（不依赖真实 LLM、浏览器、网络），共 16 个测试：

- 独立步骤成组、浏览器步骤永不分组（含工具名判定）、依赖步骤
  不分组、共享文件步骤不分组、第二道防线拆组、规划失败回退单步；
- Hive 强制顺序、运行时覆盖优先于配置、配置默认开；
- 组内思考并发且结果按组内顺序、组按顺序执行、工具执行永不并发、
  并行组失败回退顺序重跑且结果正确、开关关闭时全顺序、顺序重跑
  也失败时异常上传、执行前拆组后浏览器步骤单独成组。

运行：`python3 -m unittest tests.test_parallel -v`（或 `python -m unittest`）。

## 还没有验证的内容

- 并行执行器在真实 LLM 任务里的端到端效果：测试用的是桩思考/
  桩执行，真实模型调用的并发收益、超时与重试行为没有在本机验证。
- 控制台并行开关的真实浏览器点击：开关是静态覆盖层（与 Hive 开关
  同款，无需 React 重构建），代码已做 Node 语法检查并接入
  `build_console.sh` 的覆盖层恢复，但没有在本机用真实浏览器点过。
- 实时主循环的并行化：如上所述，本版有意不做，需要主循环重构，
  不在本版声称范围内。
- 浏览器端到端、真实模型决策链、真实蜂巢投票、真实 CodeBuddy/Trae
  派发、真实 OpenCode 命令行、Release 资产上传：v0.2.0 就没验证，
  v0.3.0 也不因并行而自动变成已验证。
